Semantic HTML

25 topics · 8 interactive exercises · covers all Friday quiz questions

This guide covers every Semantic HTML topic for the Friday lab quiz. Each topic explains WHY the element exists (not just WHAT it does), with a code example you can preview instantly. Practice your skills in the exercises section — write real HTML and see the result live.

01

What is Semantic HTML?

Q1

Semantic HTML means choosing elements based on their meaning, not their visual appearance. Compare <div class="nav"> versus <nav>: both can look identical on screen, but only <nav> tells the browser, search engine, and screen reader "this is a navigation landmark." Meaning lives in the tag, not in a class name.

Before HTML5 (2008), developers built entire pages from nested <div> and <span> elements with class names like header, sidebar, footer. This pattern is called "div soup" — it works visually, but machines cannot extract meaning from it. HTML5 introduced ~30 new semantic elements to fix this. Using them correctly improves SEO (Google ranks semantic pages higher), accessibility (screen readers navigate by landmarks), and code readability.

HTML
<!-- ✗ Div soup — machines see meaningless boxes --> <div class="header"> <div class="logo">My Site</div> <div class="nav"> <div class="nav-item"><a href="/">Home</a></div> </div> </div> <div class="main"> <div class="article">...</div> </div> <div class="footer">© 2026</div> <!-- ✓ Semantic HTML — machines understand the structure --> <header> <h1>My Site</h1> <nav> <a href="/">Home</a> </nav> </header> <main> <article>...</article> </main> <footer>© 2026</footer>

Key Points

  • Semantic = choosing tags by meaning, not appearance.
  • HTML5 added ~30 semantic elements (2008) to replace div soup.
  • Improves SEO, accessibility, and code readability.
  • Semantic elements describe structure to browsers, robots, and screen readers.
02

<header> — Page & Section Header

Q23

The <header> element represents introductory content for its nearest sectioning parent. At the top level it wraps the entire site header — logo, site title, top navigation. But it can also appear inside <article> or <section> as a localised header for that content block.

Do not confuse <header> with <head>. The <head> is invisible metadata; <header> is a visible page region. A page can have multiple header elements (one for the site, one per article), but only a single <head>. The <header> element typically contains: a logo/site title, the primary navigation (<nav>), and possibly a search form.

HTML
<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>Blog — Gachon Web Students</title> </head> <body> <!-- Page-level header --> <header> <h1>Gachon Web Blog</h1> <nav> <a href="/">Home</a> <a href="/about">About</a> <a href="/contact">Contact</a> </nav> </header> <main> <article> <!-- Article-level header (inside article) --> <header> <h2>My First HTML Page</h2> <p>Posted by Kim Jisoo · <time datetime="2026-09-05">Sep 5, 2026</time></p> </header> <p>Today I built my first webpage...</p> </article> </main> </body> </html>

Key Points

  • header = visible introductory content (NOT the invisible <head>).
  • A page can have multiple headers (site + per article).
  • Typically contains: logo, site title, primary nav.
  • Screen readers identify it as the 'banner' landmark.
03

<nav> — Navigation Landmark

Q2, Q21

The <nav> element marks a block of major navigation links. Screen readers expose it as a "navigation" landmark — visually impaired users can jump directly to navigation without reading through the whole page. Search engines also treat links inside <nav> as structural site navigation rather than body content.

You do not need to wrap every set of links in <nav> — only the primary navigation menus. Footer links to privacy policy and terms of service do not need a <nav>. Common pattern: one <nav> inside the page <header> for main navigation, and optionally a second for breadcrumbs. When you have two nav elements, add aria-label to distinguish them for screen readers.

HTML
<header> <!-- Primary site navigation --> <nav aria-label="Main navigation"> <ul> <li><a href="/">Home</a></li> <li><a href="/courses">Courses</a></li> <li><a href="/about">About</a></li> <li><a href="/contact">Contact</a></li> </ul> </nav> </header> <!-- Breadcrumb — secondary nav needs its own label --> <nav aria-label="Breadcrumb"> <ol> <li><a href="/">Home</a></li> <li><a href="/courses">Courses</a></li> <li aria-current="page">Web Programming</li> </ol> </nav> <!-- Footer links: minor, do NOT need <nav> --> <footer> <a href="/privacy">Privacy</a> · <a href="/terms">Terms</a> </footer>

Key Points

  • nav = major navigation links only (not every set of links).
  • Screen readers expose nav as a 'navigation' landmark.
  • Two navs on one page: add aria-label to distinguish them.
  • Replace <div class='nav'> with <nav> for semantic benefit.
04

<main> — The Main Content

Q3

The <main> element contains the dominant, unique content of the page — the part that differs from every other page. Navigation, headers, and footers that repeat across pages are not main content. There must be exactly one visible <main> per page. Browsers use it as the target for "skip to main content" links that screen reader and keyboard users rely on.

Think of <main> as the "jump here" destination when a keyboard user wants to skip past the repeated header and nav to get to what's actually different about this page. This is why it pairs with <a href="#main-content" class="skip-link"> — an accessibility best practice.

HTML
<!DOCTYPE html> <html lang="en"> <head><meta charset="UTF-8"><title>Courses</title></head> <body> <!-- Repeated on every page — NOT main content --> <header> <h1>My University</h1> <nav>...</nav> </header> <!-- ONE main per page — the unique content --> <main id="main-content"> <h2>Web Programming Course</h2> <p>This page is about K0126002...</p> <!-- Everything unique to this page goes here --> </main> <!-- Repeated on every page — NOT main content --> <footer> <p>&copy; 2026 Gachon University</p> </footer> </body> </html>

Key Points

  • main = the page's unique, dominant content.
  • Exactly ONE visible main per page.
  • Screen readers offer 'skip to main content' navigation.
  • header, nav, footer repeat across pages — they are NOT inside main.
05

<footer> — Page & Section Footer

Q5

The <footer> element contains information about its parent section: copyright notices, authorship, links to related documents, contact information, or a repeat of the main nav for long pages. Like <header>, it can appear at the page level or inside an <article> or <section> as a localised footer.

A page footer typically contains: copyright (&copy;), year, and company name; links to privacy policy, terms, and accessibility statement; social media links; contact details. Screen readers identify the page-level footer as the "contentinfo" landmark. Use only one page-level <footer>.

HTML
<!-- Page-level footer --> <footer> <p>&copy; 2026 Gachon University · Web Programming K0126002</p> <nav aria-label="Footer links"> <a href="/privacy">Privacy Policy</a> · <a href="/accessibility">Accessibility</a> · <a href="/contact">Contact</a> </nav> </footer> <!-- Article-level footer (meta information about the article) --> <article> <h2>Semantic HTML Deep Dive</h2> <p>Using semantic elements makes your code...</p> <footer> <p>Author: Prof. Kim · Published: <time datetime="2026-09-05">Sep 5, 2026</time></p> <p>Tags: HTML, Accessibility, SEO</p> </footer> </article>

Key Points

  • footer = information ABOUT the parent: copyright, author, links.
  • Page-level footer = 'contentinfo' landmark for screen readers.
  • Can also appear inside article/section for per-section metadata.
  • One page-level footer; multiple article/section footers are fine.
06

<section> — Thematic Grouping

Q6 (part 1)

The <section> element groups related content that belongs together thematically. The key rule: a <section> must have a heading (h1–h6) as its first child — if the group of content doesn't have (or shouldn't have) a heading, it probably shouldn't be a <section>.

A section is a named chapter or part of the page: "About Me", "Skills", "Contact". Think of it like chapters in a book — each chapter has a title and groups related paragraphs. Do not use <section> as a styling wrapper (that's what <div> is for). The question to ask: "Could this section stand as a chapter in a table of contents?" If yes, use <section>. The difference between section and article is that a section needs its surrounding context to make sense, while an article is fully independent.

HTML
<main> <!-- section groups related content under one heading --> <section id="about"> <h2>About Me</h2> <p>I am a second-year student at Gachon University...</p> <p>I enjoy web development and coffee.</p> </section> <section id="skills"> <h2>My Skills</h2> <ul> <li>HTML5</li> <li>CSS3</li> <li>JavaScript</li> </ul> </section> <section id="contact"> <h2>Contact Me</h2> <p>Email: <a href="mailto:jisoo@gachon.ac.kr">jisoo@gachon.ac.kr</a></p> </section> </main>

Key Points

  • section = thematic grouping that MUST have a heading.
  • Each section is like a named chapter with related content.
  • Don't use section as a styling wrapper — that's what div is for.
  • section needs its context; article is fully self-contained.
07

<article> — Self-Contained Content

Q4, Q25

The <article> element represents self-contained content that could be removed from the page and still make sense on its own — a blog post, a news article, a product card, a comment, a forum post. The test: could you publish this piece in an RSS feed, email, or different website and have it be understandable without the surrounding page?

Articles can be nested: a news article can contain reader comments, each of which is its own <article> inside the main one. Each article can have its own <header> (title, author, date) and <footer> (tags, related links). The key difference from <section>: an article is independently distributable; a section is part of a larger whole.

HTML
<main> <!-- A blog index page — each post is an article --> <article> <header> <h2><a href="/posts/html-basics">HTML Basics in 10 Minutes</a></h2> <p>By Kim Jisoo · <time datetime="2026-09-01">Sep 1, 2026</time></p> </header> <p>In this post I cover the essential HTML tags every web developer...</p> <footer> <p>Tags: HTML · Beginner</p> </footer> </article> <article> <header> <h2><a href="/posts/semantic-html">Why Semantic HTML Matters</a></h2> <p>By Park Minho · <time datetime="2026-09-05">Sep 5, 2026</time></p> </header> <p>Semantic HTML is not just about following rules — it directly affects...</p> <footer> <p>Tags: HTML · Accessibility · SEO</p> </footer> </article> </main>

Key Points

  • article = self-contained, independently distributable content.
  • Test: can it make sense outside this page (in RSS, email)?
  • Examples: blog post, news story, product card, comment.
  • Articles can nest (comment articles inside a post article).
08

<aside> — Tangentially Related Content

Q5 (part 2)

The <aside> element marks content that is tangentially related to the surrounding content — related but not essential to understanding it. Examples: a pull quote, a sidebar with related posts, a glossary definition box, an advertisement, author bio, or a "Did you know?" fact box.

Placed inside an <article>, an <aside> holds content tangentially related to the article. Placed directly inside <main> or <body>, it becomes a page-level sidebar. Screen readers expose it as a "complementary" landmark. The key test: if the aside were removed, would the main content still be fully understandable? If yes, it belongs in an aside.

HTML
<main> <article> <h2>CSS Flexbox Layout</h2> <p>Flexbox is a one-dimensional layout method for arranging items...</p> <p>The main axis is controlled by justify-content...</p> <!-- Tangentially related — helpful but not essential --> <aside> <h3>Quick Reference</h3> <p><code>display: flex</code> — activates flexbox</p> <p><code>flex-direction: row</code> — horizontal axis</p> <p><code>justify-content: center</code> — centre items</p> </aside> <p>The cross axis is controlled by align-items...</p> </article> <!-- Page-level sidebar --> <aside aria-label="Related articles"> <h2>You Might Also Like</h2> <ul> <li><a href="/css-grid">CSS Grid Guide</a></li> <li><a href="/responsive">Responsive Design</a></li> </ul> </aside> </main>

Key Points

  • aside = tangentially related — helpful but not essential.
  • Screen readers expose aside as 'complementary' landmark.
  • Remove it and the main content still makes complete sense.
  • Examples: sidebar, pull quote, author bio, related links.
09

<div> — The Non-Semantic Container

Q9, Q22

The <div> element is a generic block-level container with no semantic meaning. It says nothing about the content inside — it is a purely presentational tool. With HTML5 semantic elements, the golden rule is: use semantic elements first; only fall back to <div> when no semantic element fits.

When div IS the right choice: grouping elements purely for CSS layout (a flexbox row, a CSS grid column, a styling wrapper). When div is NOT the right choice: replacing <header>, <nav>, <main>, <article>, <section>, <aside>, or <footer>. A page where every structural element is a <div> is "div soup" — technically valid HTML but semantically meaningless to machines.

HTML
<!-- ✗ Div soup — everything is a div with class names --> <div class="page-wrapper"> <div class="header"> <div class="nav">...</div> </div> <div class="content"> <div class="article">...</div> <div class="sidebar">...</div> </div> <div class="footer">...</div> </div> <!-- ✓ Semantic HTML — meaningful elements where they fit --> <div class="page-wrapper"> <!-- div OK: pure CSS layout wrapper --> <header> <nav>...</nav> </header> <div class="content-grid"> <!-- div OK: CSS grid container --> <main> <article>...</article> </main> <aside>...</aside> </div> <footer>...</footer> </div>

Key Points

  • div = generic container, NO semantic meaning.
  • Use semantic elements first; div only for pure CSS layout.
  • div soup = pages built entirely from divs (bad practice).
  • class='header' does not give semantics — <header> does.

<figure> — Self-Contained Figure

Q7

The <figure> element wraps self-contained content that is referenced from the main text but could be moved to a different position or an appendix without affecting the main flow. Most commonly it wraps an image with a caption, but it can also contain code listings, tables, charts, or diagrams.

The crucial advantage: <figure> communicates a relationship — this image and this caption belong together as a unit. Without <figure>, a screen reader sees a loose image and a nearby paragraph with no connection between them. With <figure> (and its partner <figcaption>), the caption is programmatically associated with the image, so assistive technology can announce both together.

HTML
<article> <h2>Anatomy of an HTML Page</h2> <p>Every HTML file follows the structure shown in Figure 1. Notice how the body wraps all visible content.</p> <!-- figure groups image + caption as a semantic unit --> <figure> <img src="html-structure.png" alt="Diagram showing DOCTYPE, html, head, and body nesting" width="600" height="400"> <figcaption>Figure 1: The four required parts of an HTML document.</figcaption> </figure> <!-- figure can also wrap code samples --> <figure> <pre><code>&lt;!DOCTYPE html&gt; &lt;html lang="en"&gt;...&lt;/html&gt;</code></pre> <figcaption>Listing 1: The minimal HTML5 document skeleton.</figcaption> </figure> </article>

Key Points

  • figure = self-contained unit (image + caption, code + explanation).
  • Could be moved to an appendix without breaking the main flow.
  • Screen readers announce figcaption as the image's caption.
  • figure can wrap images, code, tables, or charts.
11

<figcaption> — Caption for Figure

Q8

<figcaption> provides a visible caption for its parent <figure>. It must be the first or last child element of <figure>. The caption explains what the figure shows, provides attribution, or gives a figure number.

Important distinction: figcaption is not the same as alt. The alt attribute is the text alternative for the image when it cannot be seen — a description of what the image depicts. The figcaption is a visible label for sighted users. You need both: alt for accessibility, figcaption for the visible caption. If the figcaption already fully describes the image, you can use an empty alt="" to avoid repetition for screen reader users.

HTML
<figure> <!-- alt: invisible description for screen readers --> <!-- figcaption: visible caption for everyone --> <img src="flexbox-demo.gif" alt="Animation showing flex items rearranging when flex-direction changes" width="500"> <figcaption>Figure 3: Flex direction controls the main axis orientation.</figcaption> </figure> <!-- figcaption can go FIRST or LAST inside figure --> <figure> <figcaption>Table 1: Browser support for HTML5 semantic elements.</figcaption> <table> <tr><th>Element</th><th>Chrome</th><th>Firefox</th><th>Safari</th></tr> <tr><td>&lt;main&gt;</td><td>26+</td><td>21+</td><td>7+</td></tr> <tr><td>&lt;article&gt;</td><td>6+</td><td>4+</td><td>5+</td></tr> </table> </figure>

Key Points

  • figcaption = visible caption, first or last child of figure.
  • alt = invisible screen reader description. Both are needed.
  • If figcaption fully describes the image, use alt=''.
  • Provides accessible association between image and its label.
12

<time> — Machine-Readable Dates

Q9

The <time> element marks a date, time, or duration. The content shown to the user can be in any human-readable format ("last Tuesday", "September 5th, 2026"), but the datetime attribute provides a machine-readable version that browsers, search engines, and calendar apps can parse. Without datetime, "last Friday" is meaningless to a computer; with it, it becomes datetime="2026-09-05".

Google uses <time datetime="..."> to display article publication dates in search results. iOS and Android can auto-detect dates inside <time> and offer to add them to the calendar. The datetime format follows ISO 8601: YYYY-MM-DD for dates, HH:MM for times, or YYYY-MM-DDTHH:MM for combined date-time.

HTML
<article> <header> <h2>Web Programming Lab Results</h2> <!-- Published date — ISO 8601 format in datetime --> <p>Published: <time datetime="2026-09-05">Friday, September 5, 2026</time></p> <!-- Date + time combined --> <p>Deadline: <time datetime="2026-09-12T09:00">Next Friday at 9:00 AM</time></p> </header> <p>The assignment is due in <!-- duration: P = period, W = weeks, D = days --> <time datetime="P7D">one week</time>. </p> <p>Office hours: <time datetime="14:00">2 PM</time> to <time datetime="16:00">4 PM</time> on Thursdays. </p> </article>

Key Points

  • time = date/time/duration visible to users + machine-readable datetime.
  • datetime follows ISO 8601: YYYY-MM-DD or YYYY-MM-DDTHH:MM.
  • Google reads datetime for search result snippets.
  • Browsers/phones use it to detect dates and offer calendar integration.

<address> — Contact Information

Q19

The <address> element provides contact information for its nearest ancestor <article> or <body>. Inside an article it gives the author's contact details. At the page level (inside <body> or <footer>) it gives the organisation's contact details.

A common misconception: <address> is NOT limited to postal addresses. It represents any contact information — email addresses, phone numbers, social media links, physical addresses. However, it should NOT contain non-contact information like publication dates. Browsers typically render it in italic by default; override with CSS if needed.

HTML
<!-- Article author contact info --> <article> <h2>Semantic HTML Guide</h2> <address> Written by <a href="mailto:kim.jisoo@gachon.ac.kr">Kim Jisoo</a>. Department of Computer Science, Gachon University. </address> <p>Semantic HTML is not just about following rules...</p> </article> <!-- Organisation contact info in footer --> <footer> <address> <strong>Department of Computer Science</strong><br> Gachon University<br> 1342 Seongnam-daero, Sujeong-gu<br> Seongnam-si, Gyeonggi-do 13120<br> Tel: <a href="tel:+821031234567">+82 10-3123-4567</a><br> Email: <a href="mailto:cs@gachon.ac.kr">cs@gachon.ac.kr</a> </address> </footer>

Key Points

  • address = contact info for nearest article or the whole page.
  • Contains: email, phone, physical address, social links.
  • Does NOT contain: publication dates, general paragraphs.
  • Browsers render address in italic by default (change with CSS).

<mark> — Highlighted Text

Q10

The <mark> element represents text that is highlighted or marked for reference — the HTML equivalent of a yellow highlighter pen. Its key semantic purpose is to indicate relevance in context: search results highlighting the search term, a tutor marking important passages, a diff showing what changed.

Do not confuse <mark> with <strong> or <em>. strong indicates importance (general), em indicates stress, and mark indicates contextual relevance — "this part matches what you were looking for." Browsers render it with a yellow background by default; change with CSS.

HTML
<body> <!-- Search results page — highlight the search term --> <h2>Search Results for "semantic HTML"</h2> <article> <h3>Why <mark>Semantic HTML</mark> Matters</h3> <p>This guide explains how <mark>semantic HTML</mark> improves accessibility and SEO. Using proper elements...</p> </article> <!-- Study guide — highlighting key term being defined --> <p>The <mark>DOCTYPE declaration</mark> must be the very first line of every HTML file.</p> <!-- Customise colour with CSS if yellow doesn't fit your design --> <style> mark { background-color: #ffd700; color: #000; padding: 1px 3px; border-radius: 3px; } </style> </body>

Key Points

  • mark = highlighted for contextual relevance (like a highlighter pen).
  • Different from strong (important) and em (stressed).
  • Classic use: highlight search terms in search results.
  • Yellow background by default; override with CSS.

<abbr> — Abbreviations

Q11

The <abbr> element marks an abbreviation or acronym, with the full expanded form provided in the title attribute. When users hover over the abbreviation, most browsers show the tooltip with the full form. Screen readers can also announce both the abbreviation and its expansion.

Always define an abbreviation the first time it appears in a document using <abbr>. After the first use, you can write the abbreviation bare. Common abbreviations that everyone knows (USA, HTML, CSS) may not need <abbr>, but specialist terms, organisation names, and technical acronyms always benefit from it. Browsers display a dotted underline by default.

HTML
<p> <abbr title="HyperText Markup Language">HTML</abbr> is the foundation of every web page. It works with <abbr title="Cascading Style Sheets">CSS</abbr> and <abbr title="JavaScript">JS</abbr> to create complete websites. </p> <p> This course is taught at <abbr title="Gachon University">GU</abbr> in the <abbr title="Web Programming">Web Prog</abbr> module <abbr title="Course code K0126002">K0126002</abbr>. </p> <!-- Style: dotted underline signals it has a tooltip --> <style> abbr[title] { cursor: help; text-decoration: underline dotted; } </style>

Key Points

  • abbr = abbreviation/acronym with full form in title attribute.
  • Hover tooltip shows the full expansion to users.
  • Define abbreviations on first use with abbr; later uses can be bare.
  • Dotted underline signals hover tooltip to users.

<blockquote> — Block Quotation

Q12

The <blockquote> element represents a long quotation from another source. It is block-level — it starts on its own line and receives additional indentation by default. The cite attribute (not the <cite> element) optionally provides the URL of the source. For the attribution (author name), use a <footer> or <cite> element inside the blockquote.

Do not confuse <blockquote> with the <q> element (inline quotation). Rule of thumb: if the quote requires its own paragraph, use <blockquote>. If it flows within a sentence, use <q>. Never use <blockquote> for indentation — that is a CSS job.

HTML
<article> <h2>On the Web</h2> <p>The inventor of the web described his vision clearly:</p> <!-- blockquote: multi-sentence/paragraph quote, block level --> <blockquote cite="https://www.w3.org/People/Berners-Lee/FAQ.html"> <p>The original idea of the web was that it should be a collaborative space where you can communicate through sharing information.</p> <footer> — <cite>Tim Berners-Lee</cite>, W3C Director </footer> </blockquote> <p>Today, his vision has expanded beyond what even he imagined.</p> </article>

Key Points

  • blockquote = block-level quotation from another source.
  • cite attribute = URL of the source (not shown on screen).
  • Put attribution in <footer><cite>Author</cite></footer> inside the blockquote.
  • Never use blockquote for indentation — use CSS margin instead.
17

<q> — Inline Quotation

Q13

The <q> element marks an inline (short) quotation that flows within the surrounding text. Browsers automatically add quotation marks around the content; you do not need to type them manually. The cite attribute optionally provides the source URL.

Use <q> for short quotations embedded in a sentence, and <blockquote> for longer, paragraph-level quotations. Do not add your own quotation marks inside <q> — the browser provides them (and changes them to the appropriate locale's quotation style automatically).

HTML
<p> Tim Berners-Lee once said, <q cite="https://www.w3.org/People/Berners-Lee/FAQ.html"> The web is for everyone. </q> </p> <!-- Browser auto-adds " " around q content --> <!-- In Korean browsers, it adds 「 」 or " " depending on locale --> <p> As the professor explained, <q>semantic HTML is not optional — it is the foundation of the web.</q> </p> <!-- Wrong: adding your own quotes inside q --> <!-- <q>"The web is for everyone."</q> ← removes browser's quotes -->

Key Points

  • q = inline (short) quotation within a sentence.
  • Browser auto-adds quotation marks — don't type them yourself.
  • cite attribute = URL of the source.
  • Use blockquote for paragraph-length quotes; q for sentence-embedded ones.
18

<cite> — Title of a Work

Q14

The <cite> element marks the title of a creative work — a book, film, song, poem, painting, game, website, or article. Browsers render it in italic by default. It is for TITLES only, not for the author's name or a general reference.

Do not confuse <cite> with the cite attribute. The cite attribute (on <blockquote> and <q>) holds a URL and is invisible. The <cite> element is visible on-screen text showing the title. Also do not use <cite> for the author's name — only for the work's title.

HTML
<p> We recommend reading <cite>HTML and CSS: Design and Build Websites</cite> by Jon Duckett. </p> <p> The film <cite>Parasite</cite> (2019) by Bong Joon-ho is an example of rich visual storytelling. </p> <blockquote> <p>The web must be universal.</p> <!-- cite inside blockquote: the work's title or source --> <footer>— <cite>Weaving the Web</cite>, Tim Berners-Lee</footer> </blockquote> <!-- Wrong uses: --> <!-- <cite>Tim Berners-Lee</cite> ← person name, not a work title --> <!-- <cite>https://www.w3.org</cite> ← URL, not a work title -->

Key Points

  • cite = title of a creative work: book, film, song, article.
  • Different from cite attribute (URL, invisible) on blockquote/q.
  • Do NOT use cite for author names — only for work titles.
  • Browser renders italic by default; override with CSS.
19

<code> — Inline Code

Q15

The <code> element marks inline code: variable names, function names, HTML tag names, CSS properties, file names, or any technical string that should be rendered in a monospace font to distinguish it from prose. It is an inline element and is rendered in a fixed-width (monospace) font by default.

For multi-line code blocks (a full function, a config file, a terminal command) use <pre><code>...</code></pre> — the pre preserves whitespace and line breaks, while the inner code marks it as code. Never use <code> alone for multi-line blocks (whitespace collapses). Never use <pre> alone without <code> for code — pre is for any preformatted text, not specifically code.

HTML
<!-- Inline code: variable names, tag names, properties --> <p>Use the <code>display: flex</code> property to create a flexbox container.</p> <p>Set <code>lang="ko"</code> on the <code>&lt;html&gt;</code> element for Korean pages.</p> <p>Call <code>document.getElementById('nav')</code> to select the element.</p> <p>Save the file as <code>index.html</code> in your project root.</p> <!-- Multi-line code block: pre + code together --> <figure> <pre><code>function greet(name) { return 'Hello, ' + name + '!'; } console.log(greet('Gachon'));</code></pre> <figcaption>A simple JavaScript greeting function.</figcaption> </figure>

Key Points

  • code = inline code/technical terms — renders in monospace font.
  • For multi-line code: use <pre><code>...</code></pre>.
  • pre preserves whitespace; code marks the content as code.
  • Never use <code> alone for multi-line blocks (whitespace collapses).

<pre> — Preformatted Text

Q16

The <pre> element displays text exactly as typed — all spaces, tabs, and line breaks are preserved. Browsers normally collapse multiple spaces and ignore line breaks in HTML; <pre> is the exception. It renders in a monospace font by default and is a block-level element.

The two main use cases are: (1) code blocks (always pair with <code> inside: <pre><code>...</code></pre>); and (2) ASCII art or any text where exact spacing is visually meaningful, like a terminal output transcript. Note: content inside <pre> still needs HTML escaping — < must be written as &lt;.

HTML
<!-- Code block: pre + code together --> <pre><code>&lt;!DOCTYPE html&gt; &lt;html lang="en"&gt; &lt;head&gt; &lt;meta charset="UTF-8"&gt; &lt;title&gt;Example&lt;/title&gt; &lt;/head&gt; &lt;body&gt; &lt;h1&gt;Hello&lt;/h1&gt; &lt;/body&gt; &lt;/html&gt;</code></pre> <!-- ASCII art: spaces are meaningful --> <pre> /\_____/ ( o o ) ( =^.^= ) ( (-) ) ) ( (_______) </pre>

Key Points

  • pre = preserves ALL whitespace and line breaks exactly as typed.
  • Pair with <code> inside for code blocks: <pre><code>.</code></pre>
  • < inside pre must still be escaped as &lt;
  • Block-level element, monospace font by default.
21

<details> & <summary> — Disclosure Widget

Q17, Q18

The <details> element creates a native expand/collapse widget — no JavaScript required. By default the content is hidden. The user clicks to expand it. The <summary> child provides the always-visible clickable label. All other content inside <details> (after the summary) is the expandable content.

The open attribute (no value needed) makes the widget start in the expanded state. You can listen to the toggle event in JavaScript if you need to react when it opens or closes. Use cases: FAQ sections, spoiler warnings, optional detail boxes, collapsible code samples. No library or CSS hack needed — it is built into the browser.

HTML
<!-- FAQ page using details + summary --> <h2>Frequently Asked Questions</h2> <details> <summary>What is the difference between section and article?</summary> <p>An <strong>article</strong> is self-contained and makes sense outside its page (a blog post, a comment). A <strong>section</strong> groups related content that needs the surrounding page for context.</p> </details> <details> <summary>Why should I use semantic HTML?</summary> <p>Semantic HTML improves: (1) SEO — search engines understand structure; (2) Accessibility — screen readers navigate by landmarks; (3) Maintainability — code is easier for humans to read.</p> </details> <!-- open attribute = expanded by default --> <details open> <summary>Key rule to remember</summary> <p>Use semantic elements first. Only fall back to div/span when no semantic element fits.</p> </details>

Key Points

  • details = native expand/collapse — no JavaScript needed.
  • summary = the always-visible clickable label inside details.
  • open attribute = starts expanded.
  • Use for: FAQs, spoilers, optional detail boxes.
22

<dialog> — Popup/Modal

Q20

The <dialog> element represents a popup dialog box or modal window — a native HTML modal that requires no third-party library. By default it is hidden. Call dialog.showModal() in JavaScript to display it as a true modal (blocks the rest of the page, traps focus, adds a backdrop). Call dialog.show() for a non-blocking popup. Close it with dialog.close() or by submitting a <form method="dialog"> inside it.

The native dialog element handles accessibility automatically: it traps keyboard focus inside (you cannot tab to content behind it), announces itself to screen readers, and the Escape key closes it. This is much better than a custom div-based modal which requires manual ARIA attributes and focus management.

HTML
<!-- HTML --> <button onclick="document.getElementById('confirm').showModal()"> Delete Account </button> <dialog id="confirm"> <h2>Confirm Deletion</h2> <p>This action cannot be undone. Are you sure you want to delete your account?</p> <!-- form method="dialog" closes the dialog on submit --> <form method="dialog"> <button value="cancel">Cancel</button> <button value="delete">Yes, Delete</button> </form> </dialog> <script> const dlg = document.getElementById('confirm'); dlg.addEventListener('close', function() { if (dlg.returnValue === 'delete') { alert('Account deleted (demo only)'); } }); </script>

Key Points

  • dialog = native HTML modal — no library needed.
  • showModal() = true modal (blocks page, traps focus, adds backdrop).
  • Escape key closes it automatically.
  • <form method='dialog'> inside closes the dialog on submit.
23

ARIA role Attribute

Q24

The role attribute adds an ARIA (Accessible Rich Internet Applications) semantic role to an element when no native HTML element provides the right semantics. Screen readers use the role to announce what an element IS: "button", "dialog", "navigation", "alert".

The golden rule: use native HTML first. A <button> already has the button role. A <nav> already has the navigation role. Only add a role attribute when you must use a non-semantic element (usually a <div> or <span>) to create a component that has no native HTML equivalent, or when supporting very old browsers that do not recognise newer semantic elements.

HTML
<!-- 1. Native HTML — role is implicit, no attribute needed --> <button>Submit</button> <!-- role="button" is automatic --> <nav>...</nav> <!-- role="navigation" is automatic --> <main>...</main> <!-- role="main" is automatic --> <!-- 2. ARIA role — only when native element does not exist --> <!-- Custom tab widget (no native tab element in HTML) --> <div role="tablist"> <div role="tab" aria-selected="true">HTML</div> <div role="tab" aria-selected="false">CSS</div> </div> <div role="tabpanel"> <p>HTML content here...</p> </div> <!-- Live region: screen reader announces changes immediately --> <div role="alert" id="status"> <!-- JS updates this text; screen reader reads it aloud --> </div> <!-- Never: adding role to a native element redundantly --> <!-- <nav role="navigation"> ← redundant, not wrong but unnecessary -->

Key Points

  • role = ARIA semantic role for screen readers.
  • Use native HTML first — it already has the right role.
  • Only add role when no native element fits (custom widgets).
  • role='alert' announces dynamic updates to screen readers.
24

Semantic Landmarks & Accessibility

Q21

Semantic HTML elements automatically create landmark regions that screen reader users can jump between directly, like bookmarks in a document. Each semantic element maps to a WAI-ARIA landmark role: <header> → banner, <nav> → navigation, <main> → main, <aside> → complementary, <footer> → contentinfo, <section> → region (when labelled).

Screen reader users press a shortcut key (e.g., D in NVDA, R in VoiceOver) to cycle through landmarks, instantly jumping to "navigation", "main content", or "footer" without reading every word on the page. A page with good semantic structure lets a screen reader user navigate in seconds. A page of div soup forces them to read linearly from top to bottom — potentially hundreds of lines before reaching the actual content.

HTML
<!-- This structure creates 5 landmarks automatically: --> <!DOCTYPE html> <html lang="ko"><!-- lang="ko" for Korean content --> <head> <meta charset="UTF-8"> <title>강의자료 — 웹프로그래밍</title> </head> <body> <header> <!-- landmark: banner --> <h1>Web Programming K0126002</h1> <nav> <!-- landmark: navigation --> <a href="/">홈</a> <a href="/schedule">일정</a> </nav> </header> <main> <!-- landmark: main --> <h2>Week 2: Semantic HTML</h2> <article>...</article> <aside> <!-- landmark: complementary --> <h2>관련 자료</h2> </aside> </main> <footer> <!-- landmark: contentinfo --> <p>&copy; 2026 가천대학교</p> </footer> </body> </html>

Key Points

  • Semantic elements automatically create ARIA landmark regions.
  • header→banner, nav→navigation, main→main, footer→contentinfo.
  • Screen reader users jump between landmarks with a single keystroke.
  • Div soup = no landmarks = screen reader user reads linearly from top to bottom.
